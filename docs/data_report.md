## 3. Архитектура постобработки и анализ Static vs. Temporal ошибок
Цепочка нормализаторов выполняется в строгом порядке `catalog → temporal → state → polarity → grounding`:
- **Static ошибки (каталог, полярность, спаны):**
  - *Защита метрики `case_metrics.match_facts`:* официальный эвалюатор сравнивает первую букву `object.name`, поэтому `CatalogNormalizer` исправляет ASR-опечатки и подставляет канонические имена только при сохранении первой буквы, не склеивая разные устройства.
  - *Полярность симптомов:* формулировки вида «интернет не работает» оставляют `polarity=1` (наличие симптома), тогда как «больше не пользуюсь» / «не мой тариф» переводятся в `polarity=-1`. Разговорный отказ «да нет» маркируется как `confirmation='rejected'`.
  - *Grounding:* вычисление точных Python code-point offsets `[start, end)`; при отсутствии дословного совпадения оба поля обнуляются (`span=None, quote=None`) ради 100% прохождения `validate_output`.
- **Temporal ошибки (даты и переходы состояний):**
  - Все относительные выражения («вчера», «позавчера», «через два дня», «в четверг после шести», «с прошлого месяца») резолвятся от `call.started_at` с сохранением исходной naive/aware таймзоны.
  - Для неоднозначных маркеров («недавно», «скоро», «на днях») применяется политика `preserve_anchor_with_warning`: точная дата не выдумывается, фиксируется предупреждение.
  - `StateNormalizer` закрывает предыдущее состояние (`valid_to`) только при смене значения того же `(object_key, attribute)`, изолируя параллельные объекты.

## 4. Известные ограничения и границы применимости
- Результаты на скрытом `test`-срезе не прогнозируются до завершения полного цикла SFT и оценки на официальном `val`.
- Детерминированный postprocessing исправляет нормализацию, даты, полярность и спаны только у кандидатов, извлечённых моделью, но не восстанавливает полностью пропущенные факты.
- Склеенные диалоги (414 звонков) и инверсия ролей спикеров (139 звонков) требуют корректного обучения SFT-модели на контексте всего диалога.
