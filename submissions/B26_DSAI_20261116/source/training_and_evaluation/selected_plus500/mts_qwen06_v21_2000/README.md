# Qwen3-0.6B: official2.1, step648 + 2000 calls, TOTAL≤5h

Это новый эксперимент, а не уже обученная новая версия. GPU здесь ещё не запускалась.

## Запуск
1. Откройте MTS_09_Qwen06_V21_2000_5H.ipynb в Colab, выберите GPU.
2. В первой кодовой ячейке укажите AVAILABLE_MINUTES=300 или меньший оставшийся сегодня бюджет. Отсчёт начинается ДО подключения Drive и включает всё ожидание/подготовку. Это наш лимит запуска, не обещание Google о доступной квоте.
3. Выполните ячейки1–4 по порядку. Вторая попросит ОДИН файл mts_qwen06_v21_2000_payload.zip. Не старый extended/night архив.
4. Установка и проверка данных — ячейка3. Фактическое обучение и архив — ячейка4. RUN_TRAINING=True уже задано в первой ячейке.
5. После успешной записи архива GPU отключится автоматически. Архив лежит в «Мой диск/MTS_Qwen06_V21_runs», рядом с папкой запуска. Скачайте именно *_results.zip. Папка запуска на Drive содержит полные чекпоинты.
6. Ячейка5 — только восстановление/просмотр результатов; работает после сброса ядра и не начинает обучение. Вставьте напечатанный путь RUN в EXISTING_RUN, если потерян локальный указатель.

Подписка/квота Google может закончиться раньше. Таймер освобождения ВМ — best effort: если Colab не отключился автоматически, нажмите «Среда выполнения → Отключиться и удалить среду выполнения». Выделенный GPU может расходовать квоту и без обучения.

## Данные и изменения
- Родитель: запечатанный mts_train_ready_v3, официальный пакет2.1. 2000 полных train-разговоров, 9951 фактов. Официальный val383 неизменён и не используется в обучении/подборе.
- 32 inner-dev звонка из официального TRAIN, сгруппированные по аккаунтам; это прежде использовавшийся dev, а не независимое доказательство прохождения кейса. Не подавайте его метки в обучение.
- В приоритете 362 ещё не виденных step648/возвращённых после проверки звонков. Остальные — воспроизведение прежних обучающих звонков: {"seen_extended2592": 1353, "seen_initial512": 285, "previous_quarantine_or_excluded": 106, "not_seen_remaining271": 256}. Это продолжение, не «2000 совершенно новых разговоров».
- Разговоры/роли/исходные turn.idx НЕ исправляются, ASR-шум сохраняется. Все факты выбранных звонков сохраняются; нет подбора только одного удобного факта.
- В targets убраны внутренние object.id/confirmed и необязательные цитаты/спаны. Они не нужны модели для выдачи поддерживаемой схемы; grounding проверяется по исходной реплике, роли и idx.
- Название объекта может быть пустой строкой: официальное2.1 это допускает. В частной копии общего контракта разрешён min_length=0. Никаких придуманных названий/идентификаторов.
- Автоматическая календарная эвристика НЕ переписывает конфликтующие gold-даты. 2253 из 11763 ненулевых временных полей (19.15%) исключены из loss для цифр даты: исходное значение остаётся в архивном target. Причины/возможные якоря записаны в audit/*.jsonl. Остальные части факта продолжают обучаться.
- Только 4 поля valid_from в трёх вручную просмотренных звонках приведены к started_at по официальному соглашению о неуказанной дате. Это дата фиксации, не доказанный фактический момент начала. Полные before/after и причина находятся в аудите. Иных изменений дат нет.
- Эвристики неопределённости не являются ручной проверкой всех меток. Возможны оставшиеся ошибки и нерелевантные факты в официальной онтологии. Новый подход к маскам экспериментальный; качество определят реальные предсказания.

## Обучение и общий бюджет
- База Qwen/Qwen3-0.6B, revision c1899de289a04d12100db370d81485cdf75e47ca; исходная LoRA step648, SHA256 a43fbe938f5312f541b74022d15b647ae1b8e9fefa25632df40b4b02634f69c6.
- Новый optimizer (старый optimizer не переносится), FP16 база / FP32 адаптер, r16, alpha32, dropout0, 196 модулей, LR2e-5, accumulation4, один проход, максимум500 новых обновлений. Логический размер измеряется фактически: название «0.6B» не используется как измеренное число параметров.
- Первые16 обновлений — реальное начало прохода с проверкой изменений весов и коротким dev8, а не отдельное повторяемое обучение. До них: assistant-only маски всех2000, EOS/контекст, сравнение полного и экономного loss, backward самого длинного разговора, исходный dev32.
- Затем продолжается тот же проход. Выбор промежуточного update250 делается только при достаточном запасе времени. В конце — dev32, выбор лучшего относительно исходного648, свежая загрузка базы+сохранённого адаптера, сравнение логитов и экспорт.
- При300 мин обучение заканчивается не позже220-й минуты; остаётся80 мин на оценку/проверку/архив. Желаемое завершение280 мин, процесс принудительно ограничен295 мин; отдельный таймер пытается отключить ВМ в300 мин. Один вычислительный kernel/дисковая операция может задержать мягкую остановку, поэтому есть внешний надзор.
- При меньшем бюджете резервы сокращают доступное обучение. Если500 обновлений не помещаются, сохраняется честный частичный результат. Завершение всех2000 и улучшение метрик НЕ гарантируются.
- Сохраняются initial/best/last и последние2 версии; checkpoint каждые32 обновления ИЛИ10 минут, плюс16 и финальный. Атомарные указатели обновляются только после записи и проверки контрольных сумм. Может потеряться работа после последнего полностью записанного checkpoint.

## Сравнение и ограничения
- До/после — один prompt, те же dev32, greedy, KV-cache, thinking=False, 2048 output tokens, контекст24576; без обрезания длинных звонков. Вызов ограничен120 сек. Ошибка генерации остаётся status=failed/facts=null в records; при официальном подсчёте это ноль найденных фактов, не успешный пустой ответ.
- Официальный case_metrics.py2.1 не изменён. Raw/нормализованный/serving варианты оцениваются из ОДНИХ сырых ответов; виден эффект нормализатора и фильтра подтверждений.
- Нормализатор не переставляет speaker/turn.idx и не заменяет уже валидные даты. Восстановление null допустимо лишь по однозначному относительному якорю или консервативному соглашению о неуказанной дате; иначе явная ошибка. Структурная согласованность не доказывает семантическую правильность источника.
- Agreement автоматически подтверждается только при единственной связанной реплике оператора и явном согласии клиента без отрицания/условия/изменения срока. Неопределённые соглашения видны отдельно; serving их фильтрует. Перед финальной сдачей нужно полноценное согласование с DE.
- Выбирается только полностью проверенная версия, не ухудшившая recall/temporal/state более чем на0.02 относительно собственного начала. Лучшим может остаться исходный648 — это сохраняет результат вместо сокрытия регрессии. Это внутреннее правило, не подтверждение официальных требований.
- Временная метрика считается среди СОВПАВШИХ фактов с восстановимой датой. Всегда показываются matched_facts и temporal_denominator. Fraction выше при меньшем знаменателе не доказывает улучшение всей задачи.
- Известный официальный баг recover_dates на некоторых фразах не исправляется тихо. При ошибке метрики не фабрикуются, полная проверка помечается незавершённой. Сохранённый dev32 предварительно не вызывает этот баг.
- Новые пороги относительно опубликованного2.1 baseline: temporal≥0.4506, state≥0.5145; temporal<0.4206 — критический провал. Только полный официальный383 позволит сравнивать их сопоставимо. Экономия10× параметров ИЛИ5× GPU-секунд пока не доказана: нет измерений ресурсов официального baseline.
- Полные383 и три ресурсные точки НЕ запускаются автоматически в пятичасовом обучении. Их нужно сделать отдельным последующим замером одной выбранной версии: одинаковый набор, устройство, prompt, evaluator. Квантизация не меняет логическое число параметров.

## Если запуск прерван
1. Все записанные чекпоинты лежат на Drive, локальный /content временный.
2. Если это тот же запуск и его общий бюджет ещё не истёк: укажите EXISTING_RUN, затем RESUME_NEW_CHECKPOINT=полный путь RUN/checkpoints/updateXXXXXX. Нужна вся папка с training_state.pt и snapshot_hashes.json. Источник step648 не является таким новым optimizer-checkpoint.
3. Повтор ячеек не обнуляет время/данные/порядок. Изменение payload или расписания требует отдельного явно спланированного warm-start, не «точного resume».
4. После исчерпания общего бюджета этот блокнот не продолжает обучение автоматически. Сначала заберите архив. Не используйте смену аккаунтов для обхода ограничений Google.

## Передача разработчику
В results ZIP есть export/ с base+revision descriptor, adapter, tokenizer, prompt, catalog, bridge и частной копией общего контракта. Веса базовой модели в ZIP не дублируются: скачиваются из pinned revision один раз/берутся из кэша.
Factory: ml.qwen.v21_runtime:factory, MTS_MODEL_DIR=/absolute/path/export, MTS_MODEL_DEVICE=cuda|cpu; MWS_PIPELINE_FACTORY задаётся в существующем backend. Новой HTTP-схемы/сервера нет. Режим CPU/GPU serving должен быть отдельно измерен.
Не заменяйте весь src команды этой частной копией: согласуйте только разрешение пустого ObjectRef.name и добавление bridge. В реальном репозитории проверка интеграции/полныеDE-normalizers ещё обязательны. requirements.txt — ML-зависимости, а не замена requirements всего backend.
model_manifest.json публикуется лишь после свежей загрузки сохранённого адаптера. official_case_gate_pass=null до полной оценки. В архив входит последний полный optimizer-checkpoint; другие checkpoints продолжают храниться на Drive.

Проверки на ноутбуке не являются GPU-экспериментом. Native Transformers5.3 tokenizer, CUDA loss/градиенты/ETA/reload будут проверены непосредственно в Colab до/после реального обучения. До выполнения нельзя заявлять новые ML-метрики.
