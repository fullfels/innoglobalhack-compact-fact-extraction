# Минимум три экспериментальные точки

## Сравнение способов

Оценки времени — резерв планирования после работоспособной A, а не измерения.

| Способ | Подготовка / GPU | Риск качества | Инструменты / воспроизводимость | Полезность |
|---|---|---|---|---|
| Три размера с отдельным SFT | Высокая, несколько jobs; >8–16 часов возможны | Различается способность и обучение | Нужны реальные checkpoints и одинаковый budget | Хорошая scaling curve, сейчас слишком рискованно |
| Один SFT, BF16/INT8/INT4 | Обычно 1–3 часа export/smoke + полные eval; один GPU | Квантование может повредить редким датам | Transformers+проверенный quant backend, hashes | Основной путь: чистая абляция precision |
| Три режима decoding/serving | Низкая, 0.5–2 часа настройки + eval | Ограничения контекста/output особенно опасны | Один engine, точные configs | Надёжный резерв, совпавшее качество тоже результат |
| Distillation/pruning | Высокая/непредсказуемая, новые labels и retraining | Потеря temporal/grounding | Сложнее доказать equivalence | P2, не критический путь |

## Выбранный Plan A

A = одна прошедшая аудит компактная Qwen после case-SFT, BF16 либо FP16 по hardware, greedy, batch=1, без thinking. B = тот же merged checkpoint, INT8. C = тот же checkpoint, 4-bit NF4 при поддержке backend. Общие tokenizer, prompt, max_new_tokens, context/windowing, postprocessing и список звонков. Логические параметры одинаковы: меняются числовое представление и реальные ресурсы. Квантование не обеспечивает автоматически ускорение и не доказывает 10× сокращение параметров.

Фиксировать, что quantized tensors включают scale/zero metadata, не все embeddings/lm_head обязательно квантованы; artifact size не считать просто N/2. [Официальная документация bitsandbytes](https://huggingface.co/docs/transformers/en/quantization/bitsandbytes) — источник возможностей, hardware compatibility проверять на выбранном хосте. Если engine различается, результат обозначать как сравнение системных конфигураций, а не изолированный эффект битности.

Последовательность: freeze A → quick 20-call smoke B/C → полные 383 predictions каждого → official metrics → CPU и одна GPU → pairwise errors → Pareto. B/C не используют повторное обучение. Начальная generation: do_sample=false, num_beams=1, max_new_tokens=2048 (после tokenizer-length pilot проверить, что хватает; одинаково всем). Оборванный ответ — failure, не исправлять скрытым gold/добавлением фактов. Доли truncation и retry показывать.

## Plan B: если квантование не поддерживается

За 60 минут неполадок переключиться на три воспроизводимых режима одной A в одном engine:

* A: greedy num_beams=1, use_cache=true, output budget 2048.
* B: greedy num_beams=1, use_cache=false, тот же output budget и контекст. Это контроль эффекта KV-cache; качество может совпасть, скорость может стать хуже.
* C: num_beams=2, use_cache=true, do_sample=false, тот же output budget. Это более затратный поиск; он не обязан улучшить качество.

Эти режимы гарантируют разные настройки, а не гарантированно разные результаты. Если beam search не поддерживает backend — C = тот же greedy с иным batch size 4 для offline throughput; сохранить конфигурацию, memory и batch latency, per-call latency сравнивать в одинаковом batch отдельно. Не называть B/C более экономичными до измерений. Три одинаковые метрики на разных ресурсах — честная кривая. Не менять max_new_tokens просто ради искусственного падения качества.

Plan C: сохранить стабильную A (или исходную компактную при провале SFT), провести три доступных режима, завершить API/report. Если нет ни одного обученного артефакта или GPU, прямо отметить неполное выполнение кейса. Фиктивных точек и результатов не добавлять.

## Выбор финальной конфигурации

1. Соблюдение параметров/разрешённость checkpoint, schema 100%, полные IDs и запуск экспортированной версии.
2. Проверка temporal/state gates по обеим базам и ресурса ≥10× params ИЛИ ≥5× GPU-time при наличии исходных данных. Без baseline resources статус unverified, не pass.
3. Оставить Pareto: X доминирует Y, если не хуже по выбранным качествам (temporal,state,precision,recall) и ресурсам (GPU-time,peak) и строго лучше хотя бы по одному. Не объявлять доминирование при неизвестных значениях.
4. Среди прошедших gates предпочесть стабильную конфигурацию с меньшим GPU-time при сопоставимых temporal/state и приемлемом recall. Если разница в пределах шума измерений — более воспроизводимый и простой deployment.
5. Замерить повторно экспорт победителя. Если не запускается — последняя стабильная A, не починенная на лету C без полного eval.

Для дополнительного графика разрешён `Q=(temporal_recall+state_accuracy)/2`, только если обе определены, с пометкой «внутренний агрегат». Он не заменяет метрики и не позволяет компенсировать провал temporal высоким state.
